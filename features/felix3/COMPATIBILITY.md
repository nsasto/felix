# Felix 3 compatibility

Status checked: 2026-11-04. Felix 3.0.0-preview.2 is a breaking preview; do not treat this matrix as a stable-release promise.

| Area | Felix 2.2.0 (final V2) | Felix 3.0.0-preview.2 | Cutover position |
| --- | --- | --- | --- |
| CLI | V2 command surface (`felix run`, `felix loop`, and related commands) | V3 bridge under `felix v3`; the V2 surface remains available in this preview build | Stable V3 may replace the V2 workflow; migration is required for the V3 project model |
| Project state | `.felix/` configuration, requirements database, and V2 agent profiles | Separate `.felix3/config.json`, Markdown specs with readiness frontmatter, and durable `.felix3` run/work-source state | V3 migration previews before writing and does not convert V2 requirements or agent settings |
| Harnesses | V2 agent/profile integration | Claude Code, OpenCode, Codex CLI, and Grok Build adapters passed Felix-driven workflow smokes. A Windows Grok 4.6 run completed plan/build/independent validation/review; local Cloud SSE delivered surfaced text and tool activity without persisting output text. | Install and authenticate the selected harness separately; Felix does not replace its native loop |
| Local work source | V2 requirement selection | Explicit spec, `felix v3 next`, and `felix v3 loop` over `ready-for-agent` Markdown specs | Local V3 queue is supported in the preview |
| Felix Cloud | Existing V2 sync client | Claim status and ownership checks are implemented; live output is opt-in, viewer-gated, and transient | Felix Cloud is deployed and healthy. The live activity route is present in production OpenAPI and requires authentication. A real production browser-stream run remains unverified; keep the final cutover gated |
| Recovery | V2 run recovery behavior | Durable same-checkout resume; missing local state on an active Cloud claim stops safely for recovery | Cross-machine takeover is not supported because harness session and working-tree state are local |
| Release availability | [Felix 2.2.0](https://github.com/nsasto/felix/releases/tag/v2.2.0) | [Felix 3.0.0-preview.2](https://github.com/nsasto/felix/releases/tag/v3.0.0-preview.2) is the current breaking preview | Felix 2.2.0 is the final V2 release; users need V3 to continue with Cloud work |

## Upgrade guidance

Run `felix v3 migrate --harness <claude-code|opencode|codex|grok-build>` to inspect the V3 configuration preview. Add `--apply` only after reviewing it. Migration creates separate V3 configuration and installs the provider-neutral Felix skill; it does not rewrite V2 project data. To start a new V3 project, use `felix v3 setup --harness <provider>`.

All four adapters have fixture-backed projection contracts. These describe what Felix can send to the transient Cloud view; they do not promise identical token-by-token cadence.

Grok runs headlessly with the `dontAsk` permission mode, which denies commands without a matching allow rule. Felix's sample allows common build/test command prefixes and denies destructive shell patterns; add narrow `Bash(command *)` entries for project-specific tools as needed. A bare `Bash` rule did not allow the Windows terminal tool in a headless run. Planning and review deny shell; Felix runs configured validation commands independently after building. The planning prompt directs Grok to list directory entries before reading files, and the review prompt relies on file/search inspection and Felix's validation evidence. A 2026-10-18 real local Cloud run completed all phases and delivered surfaced text over the active SSE subscription; durable Cloud events contained no text field. A separate local-only smoke using the shipped command-scoped sample completed plan/build/validation/review and executed the permitted PowerShell checker; it did not attach the Cloud viewer. The local agent-detail page could not be visually checked because the desktop browser policy blocked localhost navigation. See xAI's [permissions guide](https://docs.x.ai/build/features/permissions) and [headless CLI guide](https://docs.x.ai/build/cli/headless-scripting). Keep Grok experimental until the agent-detail UI rendering is confirmed.
